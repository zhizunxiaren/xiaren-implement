# Clarify to Build

## 概览

使用这个 skill，把模糊想法澄清到可实施、可验证的工程拆解。它组合三种思考工具：

- 苏格拉底提问法：暴露模糊词、隐藏假设、目标不清和成功标准缺失。
- 第一性原理：把问题拆到目标、角色、输入、输出、约束、不变量、失败模式和验证。
- 奥卡姆剃刀：删除不必要的抽象、功能、工具、流程步骤和系统复杂度。

这个 skill 的核心不是机械地阻止使用项目上下文，而是先判断上下文是否已经足够支撑产出：如果项目存在问题、矛盾或关键不确定性，先讨论确认；如果没有阻塞问题，可以沿用项目上下文形成文档和计划。

## 操作原则

不要把这个 skill 变成无限追问。只问会阻塞有效拆解的问题。如果已有上下文足够推进，就显式写出假设，然后继续拆解。

“阻塞有效拆解”的问题，是指不回答就无法确定目标、边界、输入、输出、风险或验收的问题。例如：做备份工具时，不知道源目录和目标位置会阻塞复制逻辑；但不确定配置格式用 JSON 还是 YAML 时，可以先按项目惯例做合理假设，不必停下来追问。

如果关键问题影响目标、边界或验收，先停下来向用户提问。如果问题只影响实现偏好或细节选择，写入“假设”并继续推进。

已有项目资料、代码、wiki、README、issue 和历史上下文是重要证据来源。读取项目资料后，必须区分：

- 已知事实：项目里已经存在的结构、术语、代码或文档。
- 当前假设：为了继续拆解而临时采用的判断。
- 待确认问题：会改变目标、边界、成功标准、文档结论或实施顺序的问题。

如果项目上下文已经清楚、一致，且没有会影响目标、边界、验收或文档结论的问题，可以基于上下文继续产出文档。只有在发现阻塞问题时才需要先停下来和用户确认。

## 入口判断

使用前先判断本次要澄清的对象是哪一种：

- 新想法：用户只有一个粗略目标，需要先定义使用者、场景、产物和成功标准。
- 现有项目或模块：用户指向某个仓库、模块、页面、API、流程或 agent，需要先从现状中提取候选功能，再向用户确认目标范围。
- 单个功能：用户已经点名一个功能，需要梳理输入、输出、状态、失败模式、验收和实施顺序。
- 文档化请求：用户说“写方案/写设计/出文档”时，先判断上下文是否足够清楚；清楚时可直接基于上下文成文，不清楚时先澄清文档要服务的功能、读者和决策。

如果用户没有明确对象，先从项目上下文中列出候选梳理对象。如果候选对象明显且无冲突，可以选定最相关对象继续；如果候选对象会导致不同文档方向，先问用户要梳理哪个项目、模块、功能或场景。

如果对象明确但目标、边界或验收不明确，先输出“当前理解”和 1-5 个关键问题。问题应该帮助用户选择方向，而不是要求用户补全所有细节。

如果对象、目标和上下文都明确，直接进入完整拆解，并在最后形成实施路径和验收检查。

## 不适用场景

- 不适用：用户只要一个明确事实、翻译、格式转换、纯信息查询或单步命令执行，或任务已经有清楚需求、边界和验收标准。

## 输出粒度选择

不要机械套完整流程。按任务复杂度选择输出粒度。

- 简化使用（对应“小型任务”模板）：单文件、单函数、单文档小改动，只保留“意图 / 实施路径 / 验收检查”。
- 正常使用（对应“中型任务”模板）：多文件、单模块、产品功能、流程设计，保留“意图 / 假设 / 简化后的范围 / 裁剪结果 / 需求拆解 / 轻量功能拆解 / 落地追踪矩阵 / 实施路径 / 验收检查”。
- 完整使用（对应“大型任务”模板）：跨模块、跨系统、长期产品方向、复杂自动化或高风险变更，使用完整模板。

如果用户明确要求“详细拆解”“完整计划”“先想清楚”，优先使用正常或完整输出。

## 工作流

### 1. 确认拆解对象和入口

先用一小段话说明：

- 本次要梳理的是哪个项目、模块、功能、流程或文档产物？
- 属于新想法、现有项目或模块、单个功能，还是文档化请求？
- 你从已有上下文中读到的事实是什么？
- 哪些只是当前假设？

如果对象不明确但项目上下文能给出单一合理对象，写明选择理由并继续；如果存在多个方向或矛盾，停下来提问。

### 2. 复述意图

在对象明确后，再复述：

- 用户真正想达成什么？
- 完成后应该产生什么具体产物？
- 谁会使用这个产物，或者哪个 agent / 系统会消费它？
- 什么结果算成功？

如果复述中有不确定部分，标记为“假设”。

### 3. 苏格拉底提问

用少量关键问题消除歧义。优先从已有上下文中自己回答，不要把所有问题都丢回给用户。

可选问题库：

澄清目标：

- 这个需求解决的真实问题是什么，而不只是表面功能是什么？
- 真正的使用者或操作者是谁？
- 它应该帮助用户做出什么决策，或完成什么动作？
- 它替代或改善了哪个现有流程？

澄清边界：

- 哪些词含义模糊或被多种方式使用？
- 哪些约束不能违反？

澄清验收：

- 输出必须满足什么条件才算有用？
- 最小的可观察进展是什么？
- 什么情况下它“看起来完成了”，但其实是误导性的？

如果某个问题会改变实施方向，要直接指出。

### 4. 第一性原理拆解

把任务拆成工程原语：

- 目标：最终状态。
- 角色：人、agent、服务、工具、系统。
- 输入：数据、文件、提示词、状态、上下文、权限。
- 输出：文件、UI 状态、API 响应、计划、日志、决策。
- 约束：安全、隐私、时间、成本、平台、仓库规则。
- 不变量：每次改动后都必须保持为真的事实。
- 失败模式：结果看似完成但实际错误的方式。
- 验证：可用的验证手段集合，例如测试、命令、截图、日志、diff、人工验收标准。它不同于最终输出里的“验收检查”；验收检查是本次结果必须执行或满足的检查清单。

把模糊名词改写成具体产物。例如，“做一个流程”应拆成状态、流转、负责人、输入、输出和验证点。

### 5. 奥卡姆剃刀裁剪

删除偶然复杂度：

- 优先修改已有结构，而不是新增系统。
- 优先一个明确文件或命令，而不是引入框架。
- 优先直接产物交接，而不是立即做实时集成。
- 优先一条可验证路径，而不是泛化编排。
- 删除不支撑成功标准的功能。
- 在人工流程没搞清楚前，暂缓自动化。
- 不要给同一个概念起两个名字，除非这个区别会改变行为。

保留复杂度的理由必须清楚：可靠性、用户体验、安全、复用、可观测性或长期维护。

裁剪结果按三类输出：

- 保留：当前就需要，且直接支撑成功标准。
- 延后：有价值，但不阻塞第一条可验证落地路径。
- 删除：不支撑目标、增加维护负担，或与现有约束冲突。

每一项都写一句理由。

### 6. 输出拆解结果

根据任务规模选择输出结构。

小型任务：

```markdown
## 意图

一段话说明拆解对象、目标和产物；如有轻量假设，直接并入本段。

## 实施路径

按顺序列出 2-5 个可执行步骤。

## 验收检查

列出能证明工作完成的具体检查。
```

中型任务：

```markdown
## 意图

一段话说明拆解对象、目标和产物。

## 假设

列出不会阻塞推进、但会影响实现细节的假设。

## 简化后的范围

用 1-3 句话说明本次范围边界：做什么、不做什么、为什么这样切。详细取舍放到“裁剪结果”。

## 裁剪结果

- 保留：
- 延后：
- 删除：

## 需求拆解

把需求写成稳定的行为或结果，并使用 `R1`、`R2` 这样的编号。

## 轻量功能拆解

用 2-5 行列出支持需求的功能，并使用 `F1`、`F2` 这样的编号。

## 落地追踪矩阵

| 需求 | 支持功能 | 实施步骤 | 验收检查 |
| --- | --- | --- | --- |

矩阵必须引用编号，例如 `R1 -> F1 -> S1,S2 -> V1`，确保每个需求都有功能、步骤和验收覆盖。

## 实施路径

按依赖顺序列出可执行、可验证的步骤，并使用 `S1`、`S2` 这样的编号。

## 验收检查

列出能证明工作落地的具体检查，并使用 `V1`、`V2` 这样的编号。
```

大型任务：

```markdown
## 意图

一段话说明拆解对象、目标和产物。

## 关键问题

只列出会阻塞实施的问题。若问题影响目标、边界或验收，先停下提问；若只影响实现偏好，转入“假设”。

## 假设

列出继续推进所依赖的假设，并标注后续需要验证的位置。

## 第一性原理模型

- 目标：
- 角色：
- 输入：
- 输出：
- 约束：
- 不变量：
- 失败模式：
- 验证：可用验证手段集合，不等同于最终必须执行的“验收检查”。

## 简化后的范围

用 1-3 句话说明本次范围边界：做什么、不做什么、为什么这样切。详细取舍放到“裁剪结果”。

## 裁剪结果

- 保留：
- 延后：
- 删除：

## 需求拆解

把需求写成稳定的行为或结果，并使用 `R1`、`R2` 这样的编号。

## 功能拆解

按用户工作流或系统边界分组能力，并使用 `F1`、`F2` 这样的编号。

## 落地追踪矩阵

| 需求 | 支持功能 | 实施步骤 | 验收检查 |
| --- | --- | --- | --- |

矩阵必须引用编号，例如 `R1 -> F1 -> S1,S2 -> V1`，确保每个需求都有功能、步骤和验收覆盖。

## 实施路径

按依赖顺序列出可执行、可验证的步骤，并使用 `S1`、`S2` 这样的编号。
```

## Walkthrough 示例

用户说：“我想做一个自动备份工具。”

应用这个 skill 时，不要直接进入“写一个备份脚本”。先做工程化拆解：

- 复述意图：用户想降低重要文件丢失风险，产物可能是一个本地备份脚本、配置文件和恢复验证流程。
- 苏格拉底提问：备份哪些目录？备份到哪里？是否需要增量？恢复时怎样证明备份可用？哪些文件不能进入备份？
- 第一性原理：输入是源目录、排除规则和目标位置；输出是备份副本、日志和恢复检查结果；不变量是不能覆盖源文件、不能泄露密钥、失败必须可见。
- 奥卡姆裁剪：先做一个显式配置文件加单次执行命令，不先做 GUI、云同步、多端账户和调度系统。
- 输出落地：需求是“按配置复制指定目录并生成日志”；实施路径是“配置格式 -> 复制逻辑 -> 排除规则 -> 日志 -> 恢复检查”；验收是“临时目录试跑、目标文件存在、排除项未复制、日志记录成功/失败”。

按小型任务模板输出时，可以写成：

```markdown
## 意图

做一个本地自动备份工具，按配置把指定目录复制到目标位置，并保留日志，降低重要文件丢失风险。

## 实施路径

1. 定义配置格式：源目录、目标目录、排除规则。
2. 实现单次备份命令：读取配置并复制文件。
3. 增加日志：记录复制成功、跳过和失败项。
4. 增加恢复检查：确认目标目录存在预期文件，且排除项没有被复制。

## 验收检查

- 用临时目录执行一次备份。
- 目标目录包含应备份文件。
- 排除规则生效。
- 日志能看出成功、跳过和失败结果。
```

中型任务可以补充一小段追踪矩阵，例如：

```markdown
## 需求拆解

- R1：按配置备份指定目录。
- R2：备份过程必须可诊断。

## 轻量功能拆解

- F1：配置读取和校验。
- F2：文件复制和排除规则。
- F3：日志记录。

## 落地追踪矩阵

| 需求 | 支持功能 | 实施步骤 | 验收检查 |
| --- | --- | --- | --- |
| R1 | F1,F2 | S1,S2 | V1,V2 |
| R2 | F3 | S3 | V3 |
```

## 决策规则

- 如果用户只要求计划，输出到实施路径为止，除非用户也要求执行。
- 如果用户要求实现，用拆解结果指导文件编辑和验证。
- 如果任务涉及仓库规则，先读取本地项目说明，再提出变更；读取到的项目知识标成“已知事实”，推断出的方向标成“当前假设”。
- 如果用户说“帮我梳理这个项目/模块”，但没有点名具体功能或目标，先从上下文提取候选梳理对象；若没有冲突，选定最相关对象继续，若会导致不同方向，先询问用户选择。
- 如果用户说“出文档”，先判断项目上下文是否已经足够支持成文；如果没有阻塞问题，可以沿用上下文生成文档；如果有问题、矛盾或缺口，先确认文档服务的功能、读者和决策。
- 每次完成本 skill 的正常或完整使用时，都必须有实施路径和验收检查。没有落地计划的输出不算完成。
- 如果任务涉及密钥、隐私、破坏性操作或生产系统，先说明安全边界，再拆解实施。
- 如果用户拒绝 MVP 表述，仍然使用奥卡姆剃刀，但把它用于实施顺序和复杂度裁剪，而不是降低产品目标。

## 常见误区

- 在项目存在矛盾、目标不清或验收缺失时，仍然直接生成文档。
- 把“写一份文档”当成最终目标，而没有判断上下文是否足够支持文档结论。
- 只输出需求或功能列表，没有实施路径和验收检查。
- 一次性梳理整个项目，导致范围太大，无法落到某个模块、功能或第一条可验证路径。
- 把所有问题都丢给用户，而不是先从已有上下文中提取事实、假设和真正阻塞的问题。

## 输出风格

直接、工程化、可执行。用户使用中文时，输出中文。苏格拉底提问法、第一性原理和奥卡姆剃刀只是工程清晰度工具，不要写成抽象哲学文章。
