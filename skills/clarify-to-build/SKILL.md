# Clarify to Build

## 概览

使用这个 skill，把模糊想法澄清到可实施、可验证的工程拆解。旧名为 `principled-breakdown`。它组合三种思考工具：

- 苏格拉底提问法：暴露模糊词、隐藏假设、目标不清和成功标准缺失。
- 第一性原理：把问题拆到目标、角色、输入、输出、约束、不变量、失败模式和验证。
- 奥卡姆剃刀：删除不必要的抽象、功能、工具、流程步骤和系统复杂度。

## 操作原则

不要把这个 skill 变成无限追问。只问会阻塞有效拆解的问题。如果已有上下文足够推进，就显式写出假设，然后继续拆解。

“阻塞有效拆解”的问题，是指不回答就无法确定目标、边界、输入、输出、风险或验收的问题。例如：做备份工具时，不知道源目录和目标位置会阻塞复制逻辑；但不确定配置格式用 JSON 还是 YAML 时，可以先按项目惯例做合理假设，不必停下来追问。

如果关键问题影响目标、边界或验收，先停下来向用户提问。如果问题只影响实现偏好或细节选择，写入“假设”并继续推进。

## 不适用场景

- 不适用：用户只要一个明确事实、翻译、格式转换、纯信息查询或单步命令执行，或任务已经有清楚需求、边界和验收标准。

## 输出粒度选择

不要机械套完整流程。按任务复杂度选择输出粒度。

- 简化使用（对应“小型任务”模板）：单文件、单函数、单文档小改动，只保留“意图 / 实施路径 / 验收检查”。
- 正常使用（对应“中型任务”模板）：多文件、单模块、产品功能、流程设计，保留“意图 / 假设 / 简化后的范围 / 裁剪结果 / 需求拆解 / 轻量功能拆解 / 落地追踪矩阵 / 实施路径 / 验收检查”。
- 完整使用（对应“大型任务”模板）：跨模块、跨系统、长期产品方向、复杂自动化或高风险变更，使用完整模板。

如果用户明确要求“详细拆解”“完整计划”“先想清楚”，优先使用正常或完整输出。

## 工作流

### 1. 复述意图

先用一小段话复述：

- 用户真正想达成什么？
- 完成后应该产生什么具体产物？
- 谁会使用这个产物，或者哪个 agent / 系统会消费它？
- 什么结果算成功？

如果复述中有不确定部分，标记为“假设”。

### 2. 苏格拉底提问

用少量关键问题消除歧义。优先从已有上下文中自己回答，不要把所有问题都丢回给用户。

可选问题库：

澄清目标：

- 这个需求解决的真实问题是什么，而不只是表面功能是什么？
- 真正的使用者或操作者是谁？
- 它应该帮助用户做出什么决策，或完成什么动作？
- 它替代或改善了哪个现有流程？

澄清边界：

- 哪些词含义模糊或被多种方式使用？
- 哪些约束不能违反？

澄清验收：

- 输出必须满足什么条件才算有用？
- 最小的可观察进展是什么？
- 什么情况下它“看起来完成了”，但其实是误导性的？

如果某个问题会改变实施方向，要直接指出。

### 3. 第一性原理拆解

把任务拆成工程原语：

- 目标：最终状态。
- 角色：人、agent、服务、工具、系统。
- 输入：数据、文件、提示词、状态、上下文、权限。
- 输出：文件、UI 状态、API 响应、计划、日志、决策。
- 约束：安全、隐私、时间、成本、平台、仓库规则。
- 不变量：每次改动后都必须保持为真的事实。
- 失败模式：结果看似完成但实际错误的方式。
- 验证：可用的验证手段集合，例如测试、命令、截图、日志、diff、人工验收标准。它不同于最终输出里的“验收检查”；验收检查是本次结果必须执行或满足的检查清单。

把模糊名词改写成具体产物。例如，“做一个流程”应拆成状态、流转、负责人、输入、输出和验证点。

### 4. 奥卡姆剃刀裁剪

删除偶然复杂度：

- 优先修改已有结构，而不是新增系统。
- 优先一个明确文件或命令，而不是引入框架。
- 优先直接产物交接，而不是立即做实时集成。
- 优先一条可验证路径，而不是泛化编排。
- 删除不支撑成功标准的功能。
- 在人工流程没搞清楚前，暂缓自动化。
- 不要给同一个概念起两个名字，除非这个区别会改变行为。

保留复杂度的理由必须清楚：可靠性、用户体验、安全、复用、可观测性或长期维护。

裁剪结果按三类输出：

- 保留：当前就需要，且直接支撑成功标准。
- 延后：有价值，但不阻塞第一条可验证落地路径。
- 删除：不支撑目标、增加维护负担，或与现有约束冲突。

每一项都写一句理由。

### 5. 输出拆解结果

根据任务规模选择输出结构。

小型任务：

```markdown
## 意图

一段话说明目标和产物；如有轻量假设，直接并入本段。

## 实施路径

按顺序列出 2-5 个可执行步骤。

## 验收检查

列出能证明工作完成的具体检查。
```

中型任务：

```markdown
## 意图

一段话说明目标和产物。

## 假设

列出不会阻塞推进、但会影响实现细节的假设。

用 1-3 句话说明本次范围边界：做什么、不做什么、为什么这样切。详细取舍放到“裁剪结果”。

## 裁剪结果

- 保留：
- 延后：
- 删除：

## 需求拆解

| 需求 | 支持功能 | 实施步骤 | 验收检查 |
```

大型任务：

## Walkthrough 示例

用户说：“我想做一个自动备份工具。”

应用这个 skill 时，不要直接进入“写一个备份脚本”。先做工程化拆解：

- 复述意图：用户想降低重要文件丢失风险，产物可能是一个本地备份脚本、配置文件和恢复验证流程。
- 苏格拉底提问：备份哪些目录？备份到哪里？是否需要增量？恢复时怎样证明备份可用？哪些文件不能进入备份？
- 第一性原理：输入是源目录、排除规则和目标位置；输出是备份副本、日志和恢复检查结果；不变量是不能覆盖源文件、不能泄露密钥、失败必须可见。
- 奥卡姆裁剪：先做一个显式配置文件加单次执行命令，不先做 GUI、云同步、多端账户和调度系统。
- 输出落地：需求是“按配置复制指定目录并生成日志”；实施路径是“配置格式 -> 复制逻辑 -> 排除规则 -> 日志 -> 恢复检查”；验收是“临时目录试跑、目标文件存在、排除项未复制、日志记录成功/失败”。

按小型任务模板输出时，可以写成：

```markdown
## 意图

做一个本地自动备份工具，按配置把指定目录复制到目标位置，并保留日志，降低重要文件丢失风险。

## 实施路径

1. 定义配置格式：源目录、目标目录、排除规则。
2. 实现单次备份命令：读取配置并复制文件。
3. 增加日志：记录复制成功、跳过和失败项。
4. 增加恢复检查：确认目标目录存在预期文件，且排除项没有被复制。

## 验收检查

- 用临时目录执行一次备份。
- 目标目录包含应备份文件。
- 排除规则生效。
- 日志能看出成功、跳过和失败结果。
```

中型任务可以补充一小段追踪矩阵，例如：

```markdown
## 需求拆解

- R1：按配置备份指定目录。
- R2：备份过程必须可诊断。

## 轻量功能拆解

- F1：配置读取和校验。
- F2：文件复制和排除规则。
- F3：日志记录。

## 落地追踪矩阵

| 需求 | 支持功能 | 实施步骤 | 验收检查 |
| --- | --- | --- | --- |
| R1 | F1,F2 | S1,S2 | V1,V2 |
| R2 | F3 | S3 | V3 |
```

## 决策规则

- 如果用户只要求计划，输出到实施路径为止，除非用户也要求执行。
- 如果用户要求实现，用拆解结果指导文件编辑和验证。
- 如果任务涉及仓库规则，先读取本地项目说明，再提出变更。
- 如果任务涉及密钥、隐私、破坏性操作或生产系统，先说明安全边界，再拆解实施。
- 如果用户拒绝 MVP 表述，仍然使用奥卡姆剃刀，但把它用于实施顺序和复杂度裁剪，而不是降低产品目标。

## 输出风格

直接、工程化、可执行。用户使用中文时，输出中文。苏格拉底提问法、第一性原理和奥卡姆剃刀只是工程清晰度工具，不要写成抽象哲学文章。
