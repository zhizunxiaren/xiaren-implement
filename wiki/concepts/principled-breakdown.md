# Principled Breakdown

## 一句话定义

Principled Breakdown 是把苏格拉底提问法、第一性原理和奥卡姆剃刀组合成一个工程拆解方法，用来把模糊想法转成可落地的需求、功能、实施路径和验收标准。

## 三个原理的分工

- 苏格拉底提问法：负责暴露模糊词、隐藏假设、目标不清和成功标准缺失。
- 第一性原理：负责把问题拆到目标、角色、输入、输出、约束、不变量、失败模式和验证。
- 奥卡姆剃刀：负责砍掉与目标无关的功能、抽象、系统和流程步骤。

## 用于需求拆解

需求拆解时先问：

- 这个需求真正解决什么问题？
- 谁会使用它？
- 什么输出才算有用？
- 哪些约束不能违反？
- 哪些成功标准可以被观察或验证？

然后把答案改写成稳定需求，而不是保留聊天式表述。

## 用于功能拆解

功能拆解时不要直接按 UI 或技术模块切分，而是先识别：

- 用户或 agent 的工作流。
- 每一步需要的输入。
- 每一步产生的输出。
- 每一步的失败模式。
- 每一步的验收方式。

再决定是否需要 UI、CLI、配置、存储、日志、MCP、skill 或自动化。

## 用于工程落地

落地时使用四层结构：

1. 需求：要达成的行为或结果。
2. 功能：支持需求的能力集合。
3. 实施：按依赖顺序排列的可执行步骤。
4. 验收：能证明结果有效的检查。

## 作为 Skill 的实现

仓库内已创建 repo-local skill：

- `skills/principled-breakdown/SKILL.md`

该 skill 适合在以下场景使用：

- 需求还比较模糊。
- 功能边界开始膨胀。
- 需要从想法转成实施计划。
- 需要判断哪些东西应该做、哪些应该砍掉或延后。
- 需要把产品想法落到工程任务。

## 常见误区

- 把苏格拉底提问法变成无限追问，导致无法推进。
- 把第一性原理变成抽象哲学，而不是工程对象拆解。
- 把奥卡姆剃刀误用成低配 MVP，而不是去掉无关复杂度。
- 没有验收标准，导致拆解看起来完整但无法证明落地。
